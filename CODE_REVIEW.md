# Code Review — Museum Flashcards

Scope: `fetch_data.py`, `docs/app.js`, `docs/shared.js`, `docs/artist-page.js`,
`docs/style.css`, and the HTML templates (`docs/study/index.html` as the
canonical copy of the 5 core-tab pages; the per-artist template embedded in
`fetch_data.py`'s `ARTIST_PAGE_TEMPLATE`).

This is a review only — nothing in the app was changed to produce it. Each
section is ranked highest-value first. Findings are backed by direct greps
against the current code, not from memory of writing it.

---

## a) Redundant code that could be centralized (JS + CSS)

### a1. Wikipedia-link-cell rendering is implemented independently 3 times
`shared.js`'s `artistLinksHtml()`, `app.js`'s `renderAllArtists()`, and
`artist-page.js` each separately: check `wiki`/`rec.wikipediaExtract` for a
match, fall back to a Wikipedia search URL, and build the
`artist-link`/`artist-link-missing` anchor tag. This is the exact
duplication that caused the real "red links never rendered red anywhere"
bug found while building the All Artists page — three copies of the same
logic drifted out of sync once, and nothing prevents it happening again.
**Option:** add one `MuseumShared.wikiLinkHtml(name, wikiInfo, linkText)`
(or similar) that all three call sites use, with `linkText` defaulting to
the artist's name so `artistLinksHtml` can call it in a loop.

### a2. `.mm-*` and `.browse-*` are near-duplicate "card grid" implementations
`.mm-grid`/`.browse-grid` and `.mm-card`/`.browse-card` differ by only a
couple of pixel values (`margin-bottom: 16px` vs. none on the grid;
`margin-bottom: 4px` vs. `10px` on the card image) and one CSS-only detail
(`.mm-card` has `display: flex; flex-direction: column; gap: 8px` that
`.browse-card` doesn't need, since it has fewer children). Both class pairs
are also listed together, redundantly, in *every* responsive breakpoint:
```css
@media (max-width: 900px) { .mm-grid, .browse-grid { grid-template-columns: repeat(2, 1fr); } }
@media (max-width: 560px) { .mm-grid, .browse-grid { grid-template-columns: 1fr; } }
```
**Option:** one shared `.card-grid`/`.work-card` base (see naming item c2 —
this is the same underlying duplication driving that naming problem too),
with `.mm-card` layering only the flex-column behavior Quiz specifically
needs on top.

### a3. Type/decade pool-filtering logic is duplicated between Quiz and Study
`buildMixPool()` (app.js:232) and the pool-building block inside
`newBrowseSet()` (app.js:435) are the same four lines verbatim:
```js
let pool = ARTWORKS.filter((a) => a.decade);
if (type) pool = pool.filter((a) => a.types.includes(type));
if (decade) pool = pool.filter((a) => a.decade === decade);
```
The "show empty state / hide grid" branches in `newMixSet()` and
`newBrowseSet()` are likewise structurally identical, just against
different element variables. **Option:** a shared
`filterArtworksPool(typeSelect, decadeSelect, {requireDecade})` and a
`toggleEmptyState(gridEl, emptyEl, isEmpty)` helper in `shared.js`.

### a4. `fetch_data.py`'s "write JSON + write JS" pattern is repeated 3 times verbatim
Once each for artworks/`ARTWORKS`, artist_wiki/`ARTIST_WIKI`, and
artists_index/`ARTISTS_INDEX` (fetch_data.py:532–568) — same
`mkdir(parents=True, exist_ok=True)` + `write_text(json.dumps(...))` +
`"// Generated by fetch_data.py..."` + `const NAME = {...}` shape each
time. **Option:** `write_json_and_js(json_path, js_path, var_name, data,
sort_keys=False)` — six blocks collapse into three one-line calls, and any
future data export follows the same path automatically.

### a5. Wikipedia search-fallback URL is (re)built in 4 separate places
Python's `build_artist_wiki_lookup` already writes a search-page fallback
URL into `wiki.url` for *every* unmatched artist — it's never null. Despite
that, `shared.js`, `renderAllArtists()`, and `artist-page.js` each also
independently reconstruct
`` `https://en.wikipedia.org/w/index.php?search=${encodeURIComponent(name)}` ``
as a defensive fallback for the case where the name isn't in the lookup at
all. That case is effectively unreachable in practice (every artist name is
sourced from the same raw data the lookup is built from), so three of the
four implementations are dead-in-practice duplication.
**Option:** centralize into one `MuseumShared.wikipediaSearchUrl(name)` and
have the three JS call sites use it purely as a type-safety fallback, not a
real code path.

### a6. `parse_birth_year` and `parse_birth_death` overlap
Both regex-scan a date string for 4-digit years (fetch_data.py:176,
:219) — `parse_birth_year` returns just the first one, `parse_birth_death`
returns first-and-last. **Option:** implement `parse_birth_year` as
`parse_birth_death(x)[0]`, or drop it and call `parse_birth_death(...)[0]`
directly at its one call site (`build_artist_wiki_lookup`).

### a7. Primary-button styling is ID-specific instead of a reusable class
`#mm-submit-btn` (style.css:319) hardcodes the "primary/accent button" look
by element ID, while every other button in `.controls` shares a generic
secondary style via the `.controls button` class. If another primary
call-to-action button is ever added elsewhere, there's no existing class to
reach for — it'll either duplicate `#mm-submit-btn`'s rules under a new ID
or (more likely) get styled inconsistently. **Option:** a `.btn-primary`
class applied via `class=`, freeing the button to work outside `.controls`
too.

### a8. (Lower priority) Study/Quiz control-bar markup is duplicated in the HTML template
The `Medium` + `Decade` + action-buttons block is hand-repeated between the
Study and Quiz `<section>`s in every one of the 5 identical core-page
copies. This is consistent with the project's explicit "no build step"
tradeoff (the whole file is already duplicated 5x on purpose), so it's
lower priority than the JS/CSS items above — flagged for completeness, not
because it's costing much today.

## b) Unused code / CSS

### b1. Per-attempt stats history stores far more than is ever read
`recordAttempt()` (app.js:48) pushes a full object — `timestamp`,
`artistGuess`, `titleGuess`, `decadeGuess`, `artistCorrect`, `titleCorrect`,
`decadeCorrect` — onto `s.history`, capped at `MAX_HISTORY_PER_ARTWORK = 20`
entries per artwork. Across the whole app, the only read of `history` is
`s.history[0]` (app.js:548), and only 3 of that single entry's 7 fields are
ever displayed (`artistGuess`/`titleGuess`/`decadeGuess`, in the Stats
table's row-title tooltip). `timestamp` and all three `*Correct` booleans
are never read anywhere, and entries 1–19 are stored but never consulted.
At the collection's current size (1,900+ artworks), this is real
localStorage overhead with zero current consumer.
**Option:** either trim `history` to a single `lastAttempt` object with
just the 3 fields actually shown (cutting stored data ~99%+ for any
heavily-quizzed artwork), or — if a "guess history" feature was the
original intent — keep it and build the feature that reads it.

### b2. `loadMixBatch`'s default label is unreachable
```js
mmPoolCount.textContent = sourceLabel || `${batch.length} works match this filter.`;
```
Both call sites (app.js:353, :465) always pass an explicit `sourceLabel`,
so the right-hand side of `||` never executes. **Option:** remove the
fallback and make `sourceLabel` a required parameter, or keep it only if a
future caller is expected to omit it.

### b3. Three `shared.js` exports have no external callers
`splitArtistNames`, `isFavorite`, and `updateFavButtons` are all in
`MuseumShared`'s returned object, but grepping `app.js` and
`artist-page.js` (the only two consumers) turns up zero external call
sites — each is only used internally within `shared.js` itself (by
`artistLinksHtml`, `makeFavButton`/`toggleFavorite`, and
`toggleFavorite`/`makeFavButton` respectively). Not broken, just publicly
exposed API surface with no current consumer.
**Option:** either drop them from the returned object (keep as private
closure functions) until something needs them externally, or leave as-is
if they're intentionally kept public for the next page/feature that will
need them — worth a one-line comment either way so it reads as a decision,
not an oversight.

## c) Non-descriptive naming

### c1. The `mm-`/`mix` prefix is a vestige of the tab's old name
The Quiz tab was originally called "Mix & Match" and was renamed to "Quiz"
some time ago (`// ---------- Quiz tab ----------` is the only place that
says so). Everything else — JS variables, CSS classes, HTML ids — still
uses the old name:
- **JS:** `mmGrid`, `mmBatch`, `mmPools`, `mmSelections`, `mmTypeFilter`,
  `mmDecadeFilter`, `mmNewSetBtn`, `mmToBrowseBtn`, `mmSubmitBtn`,
  `mmScore`, `mmEmpty`, `mmPoolCount`, `MIX_SET_SIZE`, `buildMixPool()`,
  `makeMixField()`, `renderMixGrid()`, `loadMixBatch()`, `newMixSet()`,
  `submitMix()`, and the `"mix"` keys in `TAB_SLUGS`/`SLUG_TABS`/`tabPanels`.
- **CSS:** `.mm-grid`, `.mm-card`, `.mm-field`, `.mm-select`, `.mm-score`,
  `#mm-submit-btn`.
- **HTML ids** (across all 5 core page copies): `mm-grid`,
  `mm-type-filter`, `mm-decade-filter`, `mm-new-set-btn`,
  `mm-to-browse-btn`, `mm-submit-btn`, `mm-empty`, `mm-pool-count`,
  `mm-score`, `mm-result-*`.

A reader encountering `mmGrid` or `.mm-card` cold has no way to connect it
to "Quiz." **Option:** mechanical rename to a `quiz`/`qz` prefix
(`quizGrid`, `.quiz-card`, `QUIZ_SET_SIZE`, `"quiz"` tab keys, etc.) —
large in scope (touches `app.js`, `style.css`, and all 5 template copies)
but low-risk since it's pure renaming with no behavior change.

### c2. The `browse` prefix is similarly stale — and actively misleading where it's shared
The Study tab is internally called "browse" everywhere (`browseGrid`,
`browseBatch`, `browseTypeFilter`, `browseDecadeFilter`, `BROWSE_SET_SIZE`,
`newBrowseSet()`, `loadBrowseBatch()`, `renderBrowseGrid()`, the
`"browse"` tab key, `browse-tab`/`browse-*` HTML ids) — the section
comment even preserves the awkward dual-naming as `// ---------- Study
(browse) tab ----------`. This one is worse than c1 in one specific way:
`.browse-card`/`.browse-grid` (the CSS classes) are also the classes used
by the Favorites tab and by all 633 per-artist detail pages via
`buildDisplayCard()` — contexts that have nothing to do with "Study" or
"browsing." A `.browse-card` on an artist's own detail page reads as
actively wrong, not just stale. **Option:** rename the *tab-specific* `browse*`
identifiers to `study*` (`studyGrid`, `STUDY_SET_SIZE`, `"study"` tab key),
and — separately — rename the *shared* CSS classes to something
tab-agnostic like `.work-card`/`.work-grid` or `.artwork-card`, matching
what they actually are: the app's one generic artwork-card component, not
a Study-tab-only thing. This second half ties directly to a2 above — fixing
the CSS duplication and the naming in the same pass is the efficient path.

### c3. `docs/artists.js` and `docs/artists_index.js` are indistinguishable by name
Two generated files with near-identical names hold completely different
data: `artists.js` exports `ARTIST_WIKI` (a name-keyed Wikipedia lookup);
`artists_index.js` exports `ARTISTS_INDEX` (a slug-keyed aggregate record
with genres/dates/artwork counts). Nothing in either filename hints at
which is which — a reader has to open both files to find out. This extends
to the Python-side constants that generate them:
`OUTPUT_ARTISTS_JS`/`OUTPUT_ARTISTS_JSON` (→ `ARTIST_WIKI`) vs.
`OUTPUT_ARTISTS_INDEX_JS`/`OUTPUT_ARTISTS_INDEX_JSON` (→ `ARTISTS_INDEX`).
**Option:** rename `docs/artists.js` → `docs/artist-wiki.js` (and the
matching Python constants to `OUTPUT_ARTIST_WIKI_JS`/`_JSON`), which both
disambiguates from `artists_index.js` and fixes the singular/plural
inconsistency (the file holds one lookup *per artist*, not "artists" as a
collection the way `artists_index.js` does).

### c4. `buildDisplayCard` doesn't say what it builds
It's specifically the artwork-card component (image, favorite button,
title, artist line, date) used by Study, Favorites, and artist-detail
pages. "Display card" could mean anything. **Option:**
`buildArtworkCard` — also reads naturally alongside the c2 CSS rename
(`.artwork-card`).

### c5. `WIKI` (shared.js's local alias for `ARTIST_WIKI`) is overly terse
`const WIKI = typeof ARTIST_WIKI !== "undefined" ? ARTIST_WIKI : {};`
(shared.js:11) — "wiki" alone doesn't say *artist* Wikipedia data
specifically, which matters once other Wikipedia-shaped data could
plausibly exist. **Option:** `artistWikiLookup`.

### c6. Stale/inaccurate comment in `docs/index.html`
The redirect stub's header comment says "the real app lives in study/,
quiz/, favorites/, and stats/" — missing `artists/` (the 5th core route,
added after this comment was written) and not mentioning the 633
per-artist leaf pages at all. Doesn't affect behavior (the stub redirects
unconditionally to `study/`), but it's misleading documentation for anyone
orienting themselves via that file first. **Option:** update the comment
to list all 5 core routes and mention `artist/<slug>/` as the other page
type.

### c7. `pct`/`fmtPct` slightly undersell what they do
`pct(f)` (app.js:507) computes an accuracy *ratio* (0–1), not a percent —
the `%` conversion happens later in `fmtPct`. The names are workable given
the tight surrounding context but read a beat slower than they need to.
**Option:** `computeAccuracy`/`formatAccuracy`, or at minimum
`toRatio`/`formatPercent`.
