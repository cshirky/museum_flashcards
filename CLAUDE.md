# Museum Flashcards

A static flashcard/quiz app for studying the Studio Museum in Harlem's
collection (artist, title, decade), served via GitHub Pages directly from
`docs/`. No build step — plain `<script>` tags load everything.

## Local layout

Sibling directory on disk, split off from this repo on 2026-09-02:

    studio_museum/
    ├── museum_flashcards/   — this project (the web app)
    └── artist_wiki/         — Wikipedia research dockets (separate repo)

`artist_wiki/` took a copy of `ARTIST_DATA/`, `wiki_match.py`, and a
JSON-only trim of `fetch_data.py`/`dedupe_artworks.py` at split time — it
has no web-output code and is not kept in sync with this repo. If a docket
or a Wikipedia match gets updated in one, it isn't reflected in the other.

## Working across machines

This project is used from multiple machines. Conversation history and
Claude's memory notes are local to whichever machine a session runs on —
neither transfers automatically. The only thing that carries between
machines is what's actually committed to this repo (via `git push`/`pull`),
including this file. So: durable, cross-session instructions belong here in
CLAUDE.md, not left to be re-explained per machine.

## Deploying

`git push` to `main` is the entire deploy step — GitHub Pages serves
straight from `docs/` on that branch and redeploys automatically within a
minute or two. There is no separate build/deploy command.

## Standing instructions

- Track every `.md` file the user asks to be created in this repo (git add
  it, include it in the next commit) unless they explicitly say not to.

## Architecture

- `docs/app.js` + `docs/shared.js` — all app logic (Study/Quiz/Favorites/
  Stats/All Artists tabs, favorites, hover previews, filtering). Centralized
  here; changes to shared behavior (e.g. affecting both Study and Quiz)
  belong in these files, not duplicated into HTML.
- `docs/style.css` — all styling, likewise centralized.
- `docs/{study,quiz,favorites,stats,artists}/index.html` — five **byte-
  identical** copies of the same app shell, one per tab route, so each
  works on direct load/refresh with a plain static file server (no
  server-side rewrites). Keep them in sync if markup changes; logic/style
  changes never need to touch these at all. The root `docs/index.html` is a
  separate, minimal redirect stub.
- `docs/artist/<slug>/index.html` — ~630 generated per-artist detail pages,
  one per artist. Only the `CURRENT_ARTIST_SLUG` line differs between them;
  rendering happens client-side in `docs/artist-page.js` from shared data.
  **Do not hand-edit these** — they're generated by `fetch_data.py`
  (`generate_artist_pages`). If you need to bulk-edit them (e.g. a markup
  change), either update `ARTIST_PAGE_TEMPLATE` in `fetch_data.py` and
  regenerate, or do a careful scripted find/replace across all of them —
  either way, verify the count of files changed matches the count of
  artist pages.
- `docs/data.js`, `docs/artists_index.js`, `docs/artist-wiki.js` — generated
  data, mirrored in `data/*.json` (pretty-printed, for inspection/diffing).
  Don't hand-edit either; regenerate via `fetch_data.py` or a targeted
  script like `dedupe_artworks.py`.
- `fetch_data.py` — full pipeline: fetches the collection from the Studio
  Museum's GraphQL API, resolves each artist to a Wikipedia article (URL +
  lead paragraph) via Wikipedia's REST API, dedupes true duplicate
  collection entries, writes all the `data/*.json` + `docs/*.js` files, and
  regenerates every artist page. The Wikipedia lookup step is slow
  (uncached, ~630 artists, rate-limited) — a full run takes several
  minutes. Only re-run this for a real data refresh, not for app-code
  changes.
- `wiki_match.py` — the Wikipedia artist matcher (tiered lookup, identity
  gates, `MANUAL_WIKI_MATCHES` hand-verified overrides), imported by
  `fetch_data.py` and usable standalone: `python3 wiki_match.py "Name"
  --dates "b. 1950"` for one-off checks, `--recheck
  ARTIST_DATA/ARTIST_IMAGE_NOWIKI.md` to spot artists who have since gained a
  Wikipedia page. Hand-verified matches go in `MANUAL_WIKI_MATCHES` here.
- `ARTIST_DATA/` — user-maintained artist research notes, not app-facing:
  `ARTIST_IMAGE_NOWIKI.md` (in-app artists with no confident Wikipedia
  match, with the manual review workflow documented in its intro),
  `ARTISTS_NOIMAGE_NOWIKI.md` (museum-listed artists with no artwork
  entries/images and no Wikipedia match — the background-docket pool),
  `ARTIST_NOIMAGE_WIKI.md` (no-image artists whose Wikipedia pages the
  matcher found; proposals pending review), `ARTIST_ERRATA.md`
  (hand-resolved matches and museum-side duplicate/alternate entries),
  and `dockets/` + `DOCKETS.md` — one background-research docket per
  no-Wikipedia artist (own site, social, bio, venues, press; status
  unreviewed/draft/verified lives in each docket's `Status:` line).
